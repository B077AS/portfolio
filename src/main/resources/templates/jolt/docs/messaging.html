Java and the page run in one process and exchange messages directly. There is no HTTP server and no socket between them. This page starts with one message and builds up to calling Java functions from the page like ordinary async functions.

1. Plain messages

A message is a string. Either side can send one at any time.

window.onMessage(text -> window.postMessage("You said: " + text));   // page -> Java -> page
jolt.postMessage("hi");                          // page -> Java
jolt.onMessage(message => console.log(message)); // Java -> page
  • window.onMessage(listener) in Java is called once per message from the page. window.postMessage(text) sends one to the page.
  • In the page, jolt.postMessage(text) sends to Java and jolt.onMessage(callback) registers a receiver. It returns a function that removes the receiver again.
  • You can register several listeners on either side; each gets every message.
Message listeners run on the UI thread. Never block there, for example by calling .get() on an eval result. Hand slow work to another thread and post the answer when it is ready. Section 5 shows how.

2. Sending structured data

Messages are text, so to send more than a sentence, send JSON. The page has JSON.stringify and JSON.parse built in. In Java you use any JSON library; the examples here use Gson (com.google.code.gson:gson).

jolt.postMessage(JSON.stringify({ kind: "greet", name: "Ada" }));
jolt.onMessage(raw => {
  const data = JSON.parse(raw);
  console.log(data.greeting);
});
Gson gson = new Gson();
window.onMessage(raw -> {
    JsonObject message = JsonParser.parseString(raw).getAsJsonObject();
    if (message.get("kind").getAsString().equals("greet")) {
        JsonObject reply = new JsonObject();
        reply.addProperty("greeting", "Hello, " + message.get("name").getAsString());
        window.postMessage(gson.toJson(reply));
    }
});

That works, but with many kinds of message you end up writing a big if chain on each side. Section 6 replaces it with something tidier.

3. Running a script in the page

Besides messages, Java can run JavaScript directly in the page:

window.eval("document.title")
      .thenAccept(json -> System.out.println("title = " + json));     // title = "Hello"
window.eval("document.body.style.background = 'lightyellow'");
  • eval(script) returns a CompletableFuture<String> holding the script's result as JSON, so a string comes back with its quotes.
  • It does not wait for a promise. If your script starts a fetch, the future completes with what the script itself returned, not with the fetch result. To get an answer from asynchronous page code, have the page send a message.
  • Do not build scripts by pasting user text into a string; that is how script injection happens. For data, use messages.
  • window.addInitScript(script) runs a script in every page before the page's own scripts. Use it for global setup the page needs from its first line.

4. Timing: when can I send?

Calls made right after createWindow are queued and applied in order once the web view has finished starting, so you can write createWindow, onMessage, loadHtml one after another without waiting. If you want to know when the web view is up, use window.ready(), a future that completes then (or fails if the system's web view is missing).

Your page can only receive what Java sends after the page has registered jolt.onMessage. If Java must send something as soon as the page starts, let the page ask first: send a "ready" message from the page's start-up code and have Java reply to it. The tutorial does exactly this.

5. Threads

Every Application and WebWindow method may be called from any thread, so a worker can call window.postMessage directly. What must not happen is slow work inside a listener:

window.onMessage(text -> {
    // This runs on the UI thread. Return quickly.
    Thread.startVirtualThread(() -> {
        String answer = slowLookup(text);      // seconds are fine here
        window.postMessage(answer);            // any thread may send
    });
});

If you need to run something on the UI thread yourself, use app.dispatch(() -> ...), or app.submit(() -> value) for a future with the result.

6. Calling Java functions from the page

For real apps, add a small request and response layer on top of messages. The page sends {"id": 1, "method": "notes.add", "params": {...}} and Java answers {"id": 1, "result": ...} or {"id": 1, "error": "..."}. The id ties each answer to its question, so many calls can be in flight at once. Here is the complete Java half:

import com.google.gson.Gson;
import com.google.gson.JsonObject;
import com.google.gson.JsonParser;
import io.github.b077as.jolt.WebWindow;

import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.function.Function;

/** Lets the page call Java functions by name and get the result back. */
public final class Rpc {
    private final WebWindow window;
    private final Gson gson = new Gson();
    private final Map<String, Function<JsonObject, Object>> methods = new ConcurrentHashMap<>();

    public Rpc(WebWindow window) {
        this.window = window;
        window.onMessage(this::handle);                     // runs on the UI thread
    }

    public Rpc on(String name, Function<JsonObject, Object> method) {
        methods.put(name, method);
        return this;
    }

    private void handle(String text) {
        JsonObject request = JsonParser.parseString(text).getAsJsonObject();
        long id = request.get("id").getAsLong();
        String name = request.get("method").getAsString();
        JsonObject params = request.has("params") ? request.getAsJsonObject("params") : new JsonObject();
        Thread.startVirtualThread(() -> {                   // keep the UI thread free
            JsonObject reply = new JsonObject();
            reply.addProperty("id", id);
            try {
                Function<JsonObject, Object> method = methods.get(name);
                if (method == null) throw new IllegalArgumentException("unknown method " + name);
                reply.add("result", gson.toJsonTree(method.apply(params)));
            } catch (Exception e) {
                reply.addProperty("error", String.valueOf(e.getMessage()));
            }
            window.postMessage(gson.toJson(reply));          // safe from any thread
        });
    }
}

And the page half, a call function that returns a promise:

const pending = new Map();
let nextId = 1;

jolt.onMessage(raw => {
  const reply = JSON.parse(raw);
  const waiting = pending.get(reply.id);
  if (!waiting) return;
  pending.delete(reply.id);
  if (reply.error) waiting.reject(new Error(reply.error));
  else waiting.resolve(reply.result);
});

function call(method, params = {}) {
  return new Promise((resolve, reject) => {
    const id = nextId++;
    pending.set(id, { resolve, reject });
    jolt.postMessage(JSON.stringify({ id, method, params }));
  });
}

Register Java functions and call them:

new Rpc(window)
    .on("notes.list", params -> store.list())
    .on("notes.add",  params -> store.add(params.get("text").getAsString()));
const note = await call('notes.add', { text: 'Buy milk' });
try {
  await call('notes.add', { text: '' });
} catch (e) {
  console.log(e.message);        // the text of the exception Java threw
}
  • Anything Gson can turn into JSON is a valid result: records, lists, maps, numbers, strings.
  • An exception in your Java function becomes a rejected promise on the page, so ordinary try/catch works. Only the exception's message is sent, never a stack trace.
  • Validate params as you would any input: the page is code you wrote, but a trusted origin you list is not code you wrote.

7. Java telling the page about something

Not everything is an answer to a question. When Java has news (a download finished, a new mail arrived) it can send a message the page did not ask for. Give such messages a field to tell them apart from replies, here event:

JsonObject news = new JsonObject();
news.addProperty("event", "download.finished");
news.addProperty("name", "report.pdf");
window.postMessage(gson.toJson(news));
jolt.onMessage(raw => {
  const m = JSON.parse(raw);
  if (m.event === 'download.finished') showToast(m.name + ' is ready');
});

A page can have as many jolt.onMessage receivers as it likes, so the call helper's receiver (which ignores messages without a matching id) and an event receiver can live side by side.

8. Good to know

  • app.openExternal(URI) opens an http, https or mailto address in the user's browser or mail program (since 0.2.5). It returns a future that tells you whether the system accepted the request, and throws IllegalArgumentException for any other kind of address.
  • For big or binary data use a binary channel instead of messages. For a page that talks to Java the way a website talks to a server, see serving files and requests.

Where the messages come from

Only pages your SecurityPolicy trusts can reach onMessage, so a page you did not intend to load can never call your Java handlers.
