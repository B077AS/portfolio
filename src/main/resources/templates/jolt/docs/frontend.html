Your page is normal HTML, CSS and JavaScript. The web view is Chromium (WebView2) on Windows and WebKit (WebKitGTK) on Linux, so write for both and, if you ship on both systems, try your app on both.

The loadHtml string from the first page is fine for experiments. Real apps keep the page as separate files, and this page shows how to serve them while you develop and when you ship.

Put the page in files

Create a folder of web files under src/main/resources, called ui here:

src/main/
  java/com/example/app/MyApp.java
  resources/
    ui/
      index.html
      style.css
      app.js

Then serve the folder from the jar:

window.loadResources(AppResources.classpath("ui"));

Jolt shows ui/index.html. Inside it, use ordinary relative links; they just work:

<link rel="stylesheet" href="style.css">
<script type="module" src="app.js"></script>
  • Separate CSS and JS files, images, fonts and ES modules (import) all work.
  • Use relative URLs (style.css, img/logo.png), not ones starting with a host name. Files are served from the web view itself under an address that is the same on every run (https://jolt.localhost on Windows, jolt://app on Linux), and relative URLs are the way to stay independent of it.
  • Because that address is stable, localStorage and IndexedDB keep their contents between runs.
  • No server and no port are involved. Files are read from your jar and handed to the web view.

While you develop

You do not want to rebuild a jar to see a CSS change. There are two ways to avoid that.

Serve a folder from disk

Files are re-read on every request, so reload the page (or restart the window) after you edit:

window.loadResources(AppResources.directory(Path.of("src/main/resources/ui")));

Use your frontend's dev server

If you use a tool such as Vite, point the window at its dev server to get hot reload. The server's address is an origin Jolt does not know yet, so trust it first; otherwise the navigation is blocked:

window.setSecurity(window.security().withTrustedOrigins("http://localhost:5173"));
window.loadUrl("http://localhost:5173");

A convenient pattern is to choose by a system property, so the same code does both:

String devUrl = System.getProperty("ui.url");        // run with -Dui.url=http://localhost:5173
if (devUrl != null) {
    window.setSecurity(window.security().withTrustedOrigins(devUrl));
    window.loadUrl(devUrl);
} else {
    window.loadResources(AppResources.classpath("ui"));
}
PowerShell splits -Dui.url=... at the dot. Put the whole argument in quotes: "-Dui.url=http://localhost:5173".

For release

Put the built page in src/main/resources/ui and serve it from the jar:

window.loadResources(AppResources.classpath("ui"));
  • If you use a bundler such as Vite, make it emit relative asset URLs (in Vite that is base: './') and send its output folder to src/main/resources/ui.
  • A single self-contained HTML file (Vite with vite-plugin-singlefile) can use loadHtml instead.

Any framework

React, Vue, Svelte and htmx all work, because to Jolt the page is just a page. A small typed wrapper around jolt.postMessage (for example a call<T>(method, params) function with one function per Java handler) keeps the rest of the frontend free of the bridge; the call function on the messaging page is the starting point. Parsel is a complete app built this way: a Vue page for the interface, with Java behind it for IMAP and SMTP.

Avoiding the white flash

A new window shows its background colour until the page paints. Match your page's colour so there is no white flash on a dark app, and optionally start the window hidden and show it when the page says it is ready:

WindowOptions options = WindowOptions.defaults()
        .withBackgroundColor(0x0F1117)      // same as your page's background
        .withVisible(false);                // do not show until the page is ready
WebWindow window = app.createWindow(options);
window.onMessage(m -> { if (m.equals("ready")) window.show(); });
// last line of your start-up code
jolt.postMessage("ready");

If you use the Rpc class, you could also call show() from the handler of your first call.

Developer tools

WindowOptions.defaults().withDevTools(true), then right-click and choose Inspect, or call window.openDevTools(). You get the console, network and elements panels of the underlying browser. Turn them off for release builds if you do not want users poking around.
