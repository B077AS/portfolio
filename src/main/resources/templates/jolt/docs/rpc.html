Available since 0.4.2. The messaging page ends with a request and response layer you write yourself. Jolt now has one built in: the page calls a Java function with jolt.call and gets a promise back, and Java can push events to the page. It handles JSON, errors, cancellation, progress and limits for you, so you no longer copy an Rpc class and a call() function into every project. Streaming results, interceptors and generated TypeScript types arrived in 0.5.0.

1. The smallest call

Create an Rpc, register functions by name, and attach it to a window before the page loads:

Rpc rpc = Rpc.create()
        .on("hello", call -> "Hello from Java");

rpc.attach(window);
window.loadResources(AppResources.classpath("ui"));
const text = await jolt.call('hello');      // "Hello from Java"
  • A handler runs on a virtual thread, one per call, never on the UI thread. It may block, wait on a database or take a while, and the window stays responsive.
  • What a handler returns is sent back as JSON. A handler may also return a CompletionStage; the page gets the value it completes with.
  • RPC traffic never reaches window.onMessage or jolt.onMessage, so those stay free for your own messages. One Rpc can serve several windows, and call.window() tells a handler which one asked.

2. Parameters and results

Tell on which type the page sends and Jolt decodes the JSON into it. Records work well:

record NewNote(String text, List<String> tags) {}

Rpc rpc = Rpc.create()
        .on("notes.list", call -> store.list())                                        // no parameters
        .on("notes.add", NewNote.class, note -> store.add(note.text(), note.tags()));  // one parameter
const notes = await jolt.call('notes.list');
const added = await jolt.call('notes.add', { text: 'Buy milk', tags: ['home'] });

The built-in JSON reader and writer, JsonCodec.basic(), needs no library. It handles records, enums, collections, maps, arrays, Optional, UUID and the java.time types. If your app already uses Gson or Jackson, plug it in once:

// Gson
RpcOptions options = RpcOptions.defaults().withCodec(JsonCodec.of(gson::toJson, gson::fromJson));

// Jackson
RpcOptions options = RpcOptions.defaults().withCodec(JsonCodec.of(
        mapper::writeValueAsString,
        (json, type) -> mapper.readValue(json, mapper.constructType(type))));

Rpc rpc = Rpc.create(options);

Treat everything the page sends as untrusted input and check it, exactly as you would a web form.

3. Errors

Throw an RpcException to tell the page what went wrong. It carries a code, a message and optional data, and the promise rejects with a JoltRpcError that has the same three fields:

.on("notes.get", Integer.class, id -> {
    Note note = store.find(id);
    if (note == null) throw new RpcException("not_found", "No note " + id, Map.of("id", id));
    return note;
})
try {
  await jolt.call('notes.get', 7);
} catch (e) {
  console.log(e.code, e.message, e.data);      // "not_found" "No note 7" { id: 7 }
}

Any other exception reaches the page only as code: "internal" with a generic message, so file paths and SQL never leak. It is logged and passed to rpc.onError(...). That is the safe default, but for the failures your app expects you usually want the page to see the real reason. Say so per exception type:

rpc.onException(IllegalArgumentException.class, (call, e) -> new RpcException("invalid", e.getMessage()))
   .onException(SQLException.class,            (call, e) -> new RpcException("sql", e.getMessage()));
  • The most specific type wins, as with catch clauses. Throwable.class catches the rest.
  • A handler always answers with an RpcException. It sees the exception itself, unwrapped from ExecutionException or CompletionException.
  • An exception with a handler is an expected failure: it is logged at DEBUG, not as a warning, and not given to onError. One without a handler is a bug and is reported as before.
  • While you develop, rpc.onException(Throwable.class, (call, e) -> RpcException.exposing(e)) shows every real class and message in the page.
  • An error message is cut to 4096 characters. A bad_params answer never carries the JSON library's message, because it can name your classes and fields.
  • Jolt's own codes are unknown_method, bad_params, too_many_calls, too_large, unavailable and stream_required; the page itself can also produce timeout, bad_request and not_enabled (no Rpc is attached to the window).
Changed in 0.5.0: RpcOptions.withExposeErrorMessages(true) is gone. Use the RpcException.exposing line above instead. RpcOptions also gained streamWindow, so code that calls its constructor directly must pass it: RpcOptions(codec, maxMessageChars, maxConcurrentCalls, streamWindow, executor). The with... methods are unaffected.

4. Long work: progress, cancel and timeout

A handler can take a second parameter, the RpcCall, to report progress and notice that the page gave up:

.on("export", ExportRequest.class, (request, call) -> {
    for (Page page : request.pages()) {
        call.checkCancelled();                  // throws if the page gave up
        write(page);
        call.progress(page.number());           // reaches onProgress in the page
    }
    return "done";
})
const controller = new AbortController();
const result = await jolt.call('export', { pages }, {
  signal: controller.signal,                    // controller.abort() cancels the call
  timeout: 60_000,                              // milliseconds
  onProgress: (n) => (bar.value = n),
});

An aborted signal, a passed timeout, a reload or navigation, closing the window and rpc.detach(window) all cancel the call: Java interrupts the handler's thread and drops its answer.

5. Java telling the page

Not everything is an answer. Push an event to every attached window, from any thread:

rpc.emit("notes.changed", store.count());           // every attached window
rpc.emit(window, "notes.changed", store.count());   // one window
const stop = jolt.onEvent('notes.changed', (count) => (badge.textContent = count));
// stop() unsubscribes

6. Streaming results

Available since 0.5.0. Some methods have many answers over time: lines of a log, rows of a query, steps of a job. Return a Flow.Publisher, or fill an RpcStream, and read it in the page with jolt.stream, an async iterator:

rpc.on("tail", call -> {
    RpcStream<String> out = call.stream();
    try (BufferedReader log = Files.newBufferedReader(path)) {
        for (String line; (line = log.readLine()) != null; ) {
            out.send(line);          // waits while the page is behind; throws if it gave up
        }
    }
    return null;                     // the stream ends when the handler returns
});

rpc.on("rows", call -> database.rowsPublisher());   // a Publisher is forwarded item by item
for await (const line of jolt.stream('tail', { file: 'app.log' }, { signal })) {
  append(line);                      // break (or abort) stops the producer in Java
}
  • The page sets the pace. It asks for more items as it consumes them, so at most RpcOptions.streamWindow (64 by default) are in flight. send waits, a Publisher is asked for no more, and a page cannot grant more than the window.
  • If the handler throws, the stream ends with a JoltRpcError after the items already sent. A break, an abort or a reload cancels it like any other call.
  • A stream counts as a running call until it ends, so maxConcurrentCalls applies to it.
  • A handler can return its RpcStream so that another thread keeps filling it and calls complete() or fail(error) later.
  • A plain value read with jolt.stream is a stream of one item. A streaming method called with jolt.call is answered with stream_required.

7. Interceptors

Available since 0.5.0. Code that should run around every call, such as a sign-in check, timing or logging, does not belong in each handler:

rpc.before(call -> {
    if (!session.isSignedIn() && !call.method().startsWith("auth.")) {
        throw new RpcException("unauthorized", "Please sign in");   // refuses the call
    }
});

rpc.around((call, next) -> {
    long start = System.nanoTime();
    try {
        return next.handle(call);               // run the rest of the chain and the method itself
    } finally {
        log.debug("{} took {} ms", call.method(), (System.nanoTime() - start) / 1_000_000);
    }
});

Interceptors run in the order you register them, the first one outermost, and only for methods that exist. They see the value a CompletionStage resolves to, not the stage. Whatever they throw goes through the exception handlers from section 3.

8. TypeScript types

Available since 0.5.0. If your page is written in TypeScript, let Jolt write the declarations of your Java methods, so a wrong method name, parameter or result is a compile error:

rpc.writeTypeScript(Path.of("frontend/src/jolt-api.d.ts"));    // call it at start-up while developing
const notes = await window.jolt.call('notes.list');              // Note[]
await window.jolt.call('notes.add', { txt: 'x' });               // error: no property 'txt'
for await (const note of window.jolt.stream('notes.watch')) {}   // note is a Note
  • The file has an interface per record, a type per enum and a typed window.jolt with call and stream. It is only rewritten when its text changes, so it does not disturb a dev server. rpc.typeScript() returns the text instead of writing it.
  • The types come from the declared parameter and return types of methods registered with rpc.register(controller) (next section). A CompletionStage is unwrapped, and a Publisher<T> or RpcStream<T> result is a stream.
  • A method registered with on and a lambda has no declared result, so the page sees unknown (and the parameter type only if you passed the class, as in on("notes.add", NewNote.class, handler)). To state both, use the longer form: rpc.on("notes.add", NewNote.class, Note.class, call -> store.add(call.params(NewNote.class))). The types change nothing at run time.
  • The shapes follow JsonCodec.basic(). A JSON library that renames properties or writes dates differently needs declarations of its own.
  • A record component that can be null is written name?: T | null, unless it is primitive or annotated @NonNull (any annotation with that name).

9. Annotated controllers

Available since 0.5.0. rpc.on(...) is the preferred way: the compiler checks it and it needs no reflection. If your app has a great many methods, you can group them in classes and register the objects instead:

@JoltRpc("notes")                                     // optional prefix
class NotesService {
    @JoltRpc List<Note> list() { ... }                // "notes.list"
    @JoltRpc("add") Note add(NewNote note) { ... }    // "notes.add"
    @JoltRpc String export(Request r, RpcCall call) { call.progress(50); ... }
}

class RpcErrors {
    @JoltRpcExceptionHandler                          // like rpc.onException(SQLException.class, ...)
    RpcException sql(SQLException e) { return new RpcException("sql", e.getMessage()); }
}

rpc.register(new NotesService(store)).register(new RpcErrors());

A method takes at most one parameter for what the page sends, plus optionally the RpcCall and the calling WebWindow. Everything about errors, threads and cancellation is as above. The price is that the methods are found by reflection:

  • A repeated name, a static method or a method of the wrong shape is reported when you call register (as an IllegalStateException, with nothing of that controller registered), not by the compiler.
  • Native images and trimmed (jlink) module sets need extra configuration for reflection.
  • Names are strings inside annotations.

It pays off when one class per area of the app reads better than a long list of on calls. In a Spring Boot application the beans are found for you.

10. Limits and security

  • Only pages whose origin your SecurityPolicy trusts can call, and only from the top-level document.
  • A window can have 64 calls running at once and send requests of up to 8 million characters. Both are in RpcOptions.
  • For big or binary data, use a channel instead of a call.
  • If you still have your own Rpc class from the old messaging page, delete it. Pick a method naming scheme like area.action; names starting with jolt. are reserved.
