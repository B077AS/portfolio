Never write a password or token to a file of your own. jolt-credentials is an optional module (since 0.2.1) that keeps secrets in the operating system's keystore. It needs no window and has no dependency on jolt-core, so you can use it in any Java program.

1. Add it

Add io.github.b077as:jolt-credentials:0.3.2 to your dependencies:

<dependency>
  <groupId>io.github.b077as</groupId>
  <artifactId>jolt-credentials</artifactId>
  <version>${jolt.version}</version>
</dependency>

2. Usage

CredentialStore store = CredentialStore.open("com.example.mail");
store.put("alice@example.com", password);
Optional<String> saved = store.get("alice@example.com");
store.delete("alice@example.com");
  • The service you open the store with is a namespace for your app; use its id (not blank, at most 255 characters, no /). Two apps with different services never see each other's entries.
  • The account is the name you file each secret under, such as an email address.
  • put replaces an earlier secret; get gives an empty Optional if there is none.
  • Secrets are text (UTF-8, no NUL characters).

3. In an app: remember a login

A typical use is "remember me". Do the keystore calls off the UI thread, since they can block, for example while the user unlocks the keyring:

Thread.startVirtualThread(() -> {
    try {
        CredentialStore store = CredentialStore.open("com.example.mail");
        Optional<String> saved = store.get(email);
        window.postMessage(saved.isPresent() ? "login:remembered" : "login:ask");
    } catch (CredentialStoreUnavailableException e) {
        window.postMessage("login:ask");          // no keystore: ask every time
    }
});

4. Platforms

  • Windows: the Credential Manager, with secrets up to 2560 bytes in UTF-8.
  • Linux: the Secret Service through libsecret (libsecret-1-0), which needs a running, unlocked keyring (GNOME Keyring, KWallet and KeePassXC provide one).

open throws CredentialStoreUnavailableException when there is no keystore, so catch it and fall back, for example to an encrypted vault behind a master password. Call the store off the UI thread: it can block while the user unlocks the keyring.

5. What it protects against

The keystore protects against other users of the machine and someone reading the disk. It does not protect against another program running as the same user, which can ask the keystore for the same secrets. A Java String cannot be wiped from memory, so do not keep a secret longer than you need to.
