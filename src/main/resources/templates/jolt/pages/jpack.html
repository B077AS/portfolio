Companion project

jpack, updates for Java desktop apps, made to fit Jolt.

An app ships once and then needs fixing again and again. jpack puts a small native program next to your app. It downloads each new release in the background, checks it, swaps the files in while nothing is running, and starts the new version. The jars, the bundled Java runtime and every other file.

Why it matters

A Java app is easy to build and awkward to update.

It cannot replace itself

A running Java program holds its jars open, and on Windows a file in use cannot be swapped. An app that tries to update itself in place ends up needing a second program to do it. jpack is that program, done once and done carefully.

Shipping a runtime has a cost

Bundling Java is the best thing for your users: nothing to install, and the version you tested. But a one-line fix should not mean a new 30 MB installer for everyone, and that is what a plain installer gives you.

The JDK stops at the first install

jpackage builds the install folder and the installer. Nothing in the JDK gets the second release onto the machine. jpack starts exactly where it stops.

What you get

Updates that users do not have to think about.

Updates everything

Your jars, the Java runtime, native libraries, assets, plugins, the launcher and the stub itself. A new Java version is just another part of a release.

Downloads only what changed

A release is a set of parts, each with its own hash. A new jar costs the jar and nothing else, so a bugfix can be a few megabytes instead of the whole app.

Atomic swaps

New files are unpacked next to the old ones, then switched in with folder renames that take milliseconds. A power cut halfway is finished on the next start. The app never runs half old and half new.

Rolls itself back

The previous version is kept until the new one has started. A release that cannot start is taken out again automatically and is not offered a second time.

Verified and resumable

https only, and every part is checked against its SHA-256 before it is used. A cut-off download continues with an HTTP range request instead of starting over.

You draw the interface

jpack only reports numbers: checking, 42%, ready. Show them in a launcher window, in the app, or nowhere. With the background policy there is no update code at all.

How an update happens

Only one program ever starts your app, and it is not Java.

That is the whole trick. The stub, a native program of about 1 MB on Windows and 2 MB on Linux, starts your app on its own runtime and waits. While no Java process is running, nothing is ever replaced under a live JVM: not the jars, not the runtime, not the launcher.

Your release

  • A manifest, jpack-windows-x64.json
  • One zip per part
  • Plain files on any HTTPS host
⇆
GET and Range

The stub

  • Checks and downloads
  • Verifies every part
  • Swaps files, starts programs
⇆
local, with a token

Your program

  • The app, or a launcher
  • Asks and shows progress
  • Or no code at all
  1. Start. The stub finishes any swap an earlier run left half done, then swaps in a release that is waiting.
  2. Run. It starts your app (or your launcher) on the installed runtime and waits. With the background policy it also looks for updates a few seconds after the start, and then every few hours.
  3. Download. The new release is fetched and unpacked next to the running files. Your program, or the stub itself, does this while the user works.
  4. Swap. When the program exits, the stub switches the files in and starts the new version.
  5. Trial. A release that was just swapped in is on trial. If its first start fails before it says hello, the old files are put back.
With Jolt

Five places where jpack and Jolt meet.

jpack works with JavaFX, Swing or anything that runs on the JVM. These parts fit a Jolt app especially well, because Jolt already knows how to stay small, talk to a page and call into the system from any thread.

A launcher that is a Jolt window

A launcher is a small program that runs before your app: it checks, shows the download and hands over. A Jolt window with a page is an easy way to draw "Downloading 42%". Every Jolt call is safe from any thread, so jpack's progress callback can push straight to the page.

try (Jpack jpack = Jpack.connect()) {
    UpdateCheck update = jpack.check().get(30, TimeUnit.SECONDS);
    if (update.available()) {
        rpc.emit("status", "Downloading " + update.version());
        jpack.download((received, total) ->
                rpc.emit("progress", total == 0 ? 1.0 : (double) received / total)).get();
    }
    jpack.startAfterExit("app");      // the stub swaps the files in, then starts the app
}
app.quit();                           // the launcher must exit for the swap to happen

No blank moment at hand-over

Starting a Java app and its window takes a moment. The launcher can start the app while it is still on screen and close only when the app says its window is up. A Jolt app says it with one line, right after it shows the window.

window.show();
if (Jpack.isAvailable()) {
    try (Jpack jpack = Jpack.connect()) {
        jpack.notifyShown();
    }
}
if (jpack.startNow("app").get(30, TimeUnit.SECONDS).isPresent()) {
    jpack.whenShown("app").get(60, TimeUnit.SECONDS);   // fails with the exit code if the app dies first
}
app.quit();

In a Spring Boot app, JoltRuntime.whenShown() completes once the window is on screen, which is the moment to call notifyShown().

Restart to update, in the app

No launcher at all: the app downloads while the user works and the page shows a "Restart to update" button. The page talks to Java with Jolt's own RPC.

Jpack jpack = Jpack.connect();
jpack.onReady(version -> rpc.emit("update.ready", version));      // the page shows the button
jpack.check().thenAccept(u -> { if (u.available()) jpack.download(); });

rpc.on("update.restart", call -> {
    jpack.restartAfterExit();                                       // the stub starts the new version after the swap
    app.quit();
    return null;
});

Silent updates, no code

With the background policy the stub looks for updates itself and what it downloads is used the next time the app starts. Your app contains no update code. The settings live in src/jpack/jpack.json, next to a pom that only needs a main class and an address.

{
  "mainClass": "com.example.notes.NotesApp",
  "updateUrl": "https://github.com/owner/repo/releases/latest/download",
  "policy": "background",
  "jvmArgs": ["--enable-native-access=ALL-UNNAMED"],
  "branding": { "icon": "src/jpack/icon.ico", "description": "Notes", "company": "Acme" }
}

--enable-native-access is the flag every Jolt app needs, so it belongs in jvmArgs and users never see the warning.

Links and autostart keep working

After an update the app's files move, but the stub does not. JPACK_EXE is the one file that always starts the installed app, so it is what myapp:// links, autostart entries and shortcuts should point at. Whatever the stub is started with, such as a file or a link, reaches the app, where Jolt's custom links and SingleInstance pick it up.

String exe = System.getenv("JPACK_EXE");        // null when started from the IDE
if (exe != null) {
    app.autostart().enable(List.of(exe, "--minimized"));
    app.urlSchemes().register("myapp", "My App", List.of(exe));
}
Why they suit each other

Jolt keeps the app small. jpack keeps it current.

Small stays small

A Jolt app has no bundled browser, so with its own Java runtime it is about 32 MB. jpack builds that runtime for you with jlink, picks the modules with jdeps, and from then on an update moves only the part that changed.

Java can move on

Jolt follows current Java. When you move to a newer JDK, build with it and publish: installed apps download the new runtime as just another part and swap it in with the app, even from a launcher that is still running on the old one.

Looks like your app

On Windows the stub and a renamed copy of javaw.exe carry your icon and name, so the task manager, taskbar and Explorer say "Notes" and not "Java Platform SE binary". On Linux an AppImage updates by replacing its own file and fetching only the blocks that changed.

Try it

Add the plugin, build, upload.

The plugin carries the stubs for Windows x64 and Linux x64 inside its jar, so you do not need Rust. Your app's jar must be runnable with its dependencies (a shaded jar), or set includeDependencies to copy them next to it.

<plugin>
  <groupId>io.github.b077as</groupId>
  <artifactId>jpack-maven-plugin</artifactId>
  <version>0.1.3</version>
  <executions>
    <execution>
      <goals><goal>package</goal></goals>
    </execution>
  </executions>
  <configuration>
    <mainClass>my.app.Main</mainClass>
    <updateUrl>https://github.com/owner/repo/releases/latest/download</updateUrl>
  </configuration>
</plugin>
target/jpack/
  image/windows-x64/   the install folder: MyApp.exe, jpack.json, runtime/, app/
  dist/                MyApp-1.0.0-windows-x64.zip   (or .tar.gz, or an AppImage on Linux)
  release/             jpack-windows-x64.json + one file per part   <- upload all of these

Wrap image/ in an installer (Inno Setup, WiX, a .deb) or hand out the archive. Publishing an update means attaching every file of release/ to a GitHub release. Installed copies pick it up on their next check. The optional jpack-api library, with no dependencies and Java 17 or newer, is what the code above uses. Packaging in the docs

Safety

What jpack refuses to do.

RuleWhat it means
https onlyThe update address and every file address must be https://. Plain http:// is accepted only for localhost, to test locally.
Every part is verifiedChecked against the SHA-256 in the manifest before it is unpacked. A mismatch discards the download.
Paths stay insideA part name or a path that would land outside the install folder makes the part unusable.
The channel is localThe stub listens on 127.0.0.1. Each program it starts gets its own one-time token, and nothing else can ask it to download or restart.
A swap never half-happensNothing installed is touched until a release is complete and verified. A swap that cannot finish is undone and retried later.
Bad releases roll backA release that crashes on its first start is rolled back and not offered again. Publishing an earlier release again rolls everyone back to it.
